# Type4Me Reference Implementation

## Purpose

Morie's macOS voice-input foundation is **not** a greenfield implementation.

Type4Me is the reference implementation for input infrastructure that has already accumulated real-world behavior, edge cases, fixes, tests, packaging knowledge, and application compatibility lessons.

Reference repository:

- `https://github.com/joewongjc/type4me`
- branch: `main`

Morie should selectively extract/adapt proven behavior from Type4Me, modernize it for macOS 27 and current Apple APIs, and intentionally leave behind Type4Me's provider/runtime complexity.

## Migration principle

> Reuse proven behavior, not historical complexity.

Before implementing a Phase 0 subsystem from scratch, inspect the corresponding Type4Me implementation, tests, and relevant review/design documents.

The desired outcome is not a direct fork. It is a smaller Morie-native implementation that preserves the hard-won reliability behavior.

## Priority reference areas

### 1. Hotkey lifecycle

Primary source:

- `Type4Me/Input/HotkeyManager.swift`
- `Type4MeTests/HotkeyStateMachineTests.swift`
- archived multi-hotkey review/development reports where useful

Important lessons to preserve/adapt:

- press/release state is a state machine, not merely two NSEvent callbacks;
- key repeat, modifier-only keys, left/right modifiers and function/media/mouse inputs have platform edge cases;
- stale hold state / safety timer cleanup matters;
- synthetic events generated by Morie must not re-trigger hotkeys;
- active recording ownership and busy conflicts need explicit handling;
- stop/abort/reset behavior must be idempotent and recoverable.

Morie V0 may expose a much smaller shortcut feature set, but should not discard the state-machine reliability lessons.

### 2. Audio capture / recording session

Primary source:

- `Type4Me/Audio/AudioCaptureEngine.swift`
- `Type4Me/Session/RecognitionSession.swift`

Important lessons to preserve/adapt:

- explicit microphone permission handling;
- device disappearance and route behavior;
- start/stop lifecycle ownership;
- immediate graph/session detachment on stop;
- cleanup of delegates/callbacks/buffers;
- avoiding microphone warm-up behavior that unintentionally changes Bluetooth headset mode;
- recoverability after failure;
- recording generation/session identity where asynchronous results can arrive late.

Morie should use the current Apple Speech/audio pipeline, but not forget these lifecycle concerns.

### 3. Target app, focus and text delivery

Primary source:

- `Type4Me/Injection/TextInjectionEngine.swift`
- current-focus-injection design/review documents
- related App/Session integration

Important lessons to preserve/adapt:

- do not deliver back into Morie itself;
- no-valid-target behavior must preserve the user's result rather than lose it;
- clipboard fallback timing differs across native and Electron apps;
- clipboard restore must be change-count-aware so it does not overwrite a later user copy;
- synthetic Cmd+V events should be marked and ignored by the hotkey path;
- Accessibility calls need bounded timeouts and defensive handling;
- focused element/app state can change during the recording session;
- real compatibility testing matters more than a single AX happy path.

The current Morie `TextInjector` is therefore provisional until it has been reconciled with these proven patterns.

### 4. Recognition session orchestration

Primary source:

- `Type4Me/Session/RecognitionSession.swift`
- `Type4MeTests/RecognitionSessionTests.swift`

Important lessons to preserve/adapt:

- one authoritative session/state owner;
- stale asynchronous events from a previous recording must not mutate the current recording;
- stop/finalization ordering matters;
- delivery and post-processing belong to one explicit lifecycle;
- failure reporting must be tied to the active recording generation;
- session cleanup must happen on every terminal path.

Morie removes provider/LLM complexity but should retain the lifecycle discipline.

### 5. Apple Speech

Inspect Type4Me's Apple Speech implementation and previous behavior for:

- streaming partial results;
- authorization;
- locale behavior;
- cancellation/finalization;
- interaction with session state.

Morie must then modernize the recognition implementation to the latest macOS 27 Speech APIs (`SpeechAnalyzer`, `SpeechTranscriber`, current asset/input APIs) rather than preserving an old API solely for compatibility.

### 6. Permissions and onboarding

Reference Type4Me's permission/onboarding logic for real macOS behavior around:

- Microphone;
- Speech Recognition;
- Accessibility/event monitoring;
- checking again after Settings changes;
- clear user-visible failure/recovery paths.

Morie's visual implementation must use native macOS 27 system UI per `docs/ui-design.md`.

### 7. Later-phase reusable lessons

When those phases start, inspect Type4Me before designing from zero:

- hotword/vocabulary storage and use;
- correction learning / user-edit observation;
- History persistence semantics;
- IntelliSense and revise logic that genuinely improves personalized input;
- packaging/signing/release edge cases.

Do not import these early merely because they exist.

## Explicitly do not inherit

Morie does not inherit these Type4Me architecture choices by default:

- large ASR provider enum/registry/factory system;
- large LLM provider matrix;
- cloud-provider settings UI;
- SenseVoice / sherpa-onnx runtime;
- Silero VAD when Apple capability satisfies the requirement;
- Qwen3-ASR Python/MLX server;
- CppJieba when NaturalLanguage is sufficient;
- pricing registry/subscription variants;
- compatibility support for old platform APIs;
- provider credentials and account surfaces irrelevant to Private V0.

Any external dependency proposed from Type4Me remains subject to Morie's explicit owner-approval gate. Existing use in Type4Me is not permission to introduce it in Morie.

## Phase 0 audit checklist

Before M-002 is considered implementation-complete, reconcile Morie against at least:

- [ ] `HotkeyManager.swift` behavior relevant to hold-to-talk
- [ ] `HotkeyStateMachineTests.swift`
- [ ] `AudioCaptureEngine.swift` start/stop/cleanup behavior
- [ ] `RecognitionSession.swift` generation/state/finalization behavior
- [ ] `RecognitionSessionTests.swift`
- [ ] `TextInjectionEngine.swift` synthetic events / fallback / clipboard restore
- [ ] current-focus-injection decisions
- [ ] permission/onboarding behavior
- [ ] Apple Speech implementation and migration gaps

For each area, the M-002 task document should record one of:

- `ADOPT` — behavior/implementation can move nearly directly;
- `ADAPT` — keep the proven behavior but rewrite around current Morie/macOS 27 APIs;
- `DROP` — Type4Me behavior is unnecessary for Morie's V0, with reason.

## Current assessment

The first Morie Phase 0 skeleton proved repository shape and basic control flow, but parts of it are intentionally provisional. In particular, the simplistic hotkey/audio/injection paths must be reconciled with Type4Me before they can be treated as production-ready.

This is preferable to silently treating a new simplified implementation as more mature than the existing reference code.
